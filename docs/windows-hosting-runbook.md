Ниже описана дополнительная защита, установленная на существующем VPS через прежний вход в консоль Timeweb.

Источник — [relay-watchdog.py](../ops/windows-hosting/relay-watchdog.py), [служба](../ops/windows-hosting/olympiad-relay-watchdog.service) и [таймер](../ops/windows-hosting/olympiad-relay-watchdog.timer). На VPS скрипт находится в `/usr/local/libexec/olympiad-relay-watchdog.py`, units — в `/etc/systemd/system/`; владелец root, запись другим запрещена. Таймер включён и проверяет статическую главную страницу по loopback каждые20секунд. Он не обращается к рабочим API/базе/секретам; сбой Cloudflare API при исправной статике не приводит к остановке SSH.

Для восстановления нужны три последовательных сбоя одной сессии возрастом от60с. Перед TERM повторно проверяются страница, точный loopback-порт, PID, время создания, UID выделенного пользователя и бинарный файл sshd. Неизвестный/сменившийся владелец, несколько PID, другой адрес, молодое или уже исправное соединение не завершаются. Затем Windows-supervisor создаёт новый туннель. Служба имеет только loopback-сетевой доступ, системные файлы доступны на чтение, запись — в закрытый `/run/olympiad-relay-watchdog`; SSH-ограничения и30с/3 сохраняются.

Проверка: `systemctl is-active olympiad-relay-watchdog.timer`, `systemctl show olympiad-relay-watchdog.service -p Result -p ExecMainStatus`, `cat /run/olympiad-relay-watchdog/state.json`, `journalctl -u olympiad-relay-watchdog.service`. Нормально: таймер active, Result=success, состояние healthy/failures0; сама oneshot-служба между запусками inactive. Отключение только этой защиты: `systemctl disable --now olympiad-relay-watchdog.timer`; Node, Caddy, данные и действующий SSH от этого не останавливаются. Установочный журнал/манифест — `/root/olympiad-relay-watchdog-install-20261016T062754Z`.

Семь проверок безопасности проходят и на Windows, и на Linux с подменёнными сигналами/сетью: `python -m unittest discover -s tests -p relay_watchdog_test.py -v`. На работающем VPS подтверждены повторные healthy-проверки и права службы; намеренный сбой живого проведения не создавали. Все4 адреса, TLS, файлы и ПМ01 проверены, снимок до сбоя подтверждает сохранность29 попыток/540 ответов. Локальные частные отчёты — `updates/relay-watchdog-20261016`.

## Восстановление туннеля после фактической перезагрузки15октября

Перезапуск iRU в13:58МСК подтвердил локальный автозапуск, но выявил зависший серверный SSH-сеанс: удалённый13100 занят, новый SSH сразу выходит с `remote port forwarding failed`. В существующем `Match User olympiad-relay` файла`/etc/ssh/sshd_config` теперь стоят `ClientAliveInterval 30` и `ClientAliveCountMax 3`. До правки сохранена копия в`/root/olympiad-relay-recovery-20261015T111358Z/sshd_config.before`; синтаксис`sshd -t` и reload`ssh` успешны, эффективные настройки проверены отдельно для relay и root. Прочие ограничения прежние. Это позволяет серверу освобождать потерянное соединение; уже существующие сеансы нужно переподключить, чтобы они приняли новую настройку. Собственный SSH ПК контролируемо переподключён, HTTPS и все4 адреса/ПМ01 проверены. Node/Caddy не останавливались, попытки/ответы/секреты сохранены; частные проверки в`updates/relay-recovery-20261015`.

При повторении проверять локальные3100/3180, журнал`host-supervision/ssh.stderr.log`, PID и свежесть`cloud-mirror/status.json`. Не запускать второй SSH поверх supervisor. Не освобождать неизвестный процесс на VPS без проверки пользователя и команды. После реального перезапуска байты пробной SQLite могут измениться из-за открытия/контрольной точки; проверять согласованность и содержимое, а неизменность секретов — отдельными SHA-256. Резервный адрес [Pages](https://olympiad-gkts.pages.dev/) использует ту же официальную базу.

По просьбе пользователя добавлен механизм копирования Cloudflare → ПК. Он сохраняет также попытки резервного адреса. CSV защищает текстовые поля от формул Excel; если Excel удерживает основной CSV, записывается запасной файл, а SQLite/JSON продолжают обновляться. Папка и отдельный закрытый ключ ограничены текущим пользователем Windows; не публиковать и не отправлять их участникам.

## Ранее подготовленный прямой маршрут (не включён)

Следующий раздел относится к прежнему `olympiada.gorlkts.ru` при отдельно подтверждённом публичном WAN. Для текущего подключения через Timeweb он не применяется; не запускайте второй внешний Caddy или правила роутера вместо работающего туннеля.

`Браузер участника → HTTPS:443 → роутер → Caddy → 127.0.0.1:3100 → существующая SQLite`.

[Caddyfile](../ops/windows-hosting/Caddyfile) обслуживает только `olympiada.gorlkts.ru`, автоматически получает публичный сертификат и проксирует в существующий сервер. [Общие правила](../ops/windows-hosting/olympiad-routes.caddy) закрывают внешние страницы/API организатора; панель остаётся доступна владельцу на `http://127.0.0.1:3100/admin.html`. API получает `private, no-store`; конфигурация не записывает токены/пароли в журнал и не открывает Node на сетевом интерфейсе.

Локальная [репетиция](../ops/windows-hosting/Caddyfile.rehearsal) использует только loopback: HTTP 3180, HTTPS 3443 и служебный API Caddy 3181. Её внутренний сертификат проверяют отдельным доверенным CA-файлом только в проверочном процессе; системное доверие/hosts/DNS не меняют. Это не публичный сертификат целевого домена. Продуктивный Caddyfile на этом этапе только адаптируют/проверяют синтаксически, не запускают запрос публичного сертификата. Файлы находятся в `ops/`, вне путей автоматического развёртывания Cloudflare.

Caddy 2.11.7 получен из [официального выпуска](https://github.com/caddyserver/caddy/releases/tag/v2.11.7); SHA-256 Windows ZIP сверен с метаданными выпуска: `0a1edc0b799512051c57071ce0e798d3f2cf67dc98171366f1d2b326072e3b06`. Исполняемый файл находится в приватной локальной папке подготовки, не в Git; служба не установлена.

Репетиция прошла восемь проверок HTTP/HTTPS: health и единственный `private, no-store`, байтовое совпадение HTML/фото/страницы свидетельства с исходным сервером, закрытые admin/секреты/PM01, недоступная чужая попытка с тем же отказом, что у исходного сервера. Все три порта слушали только `127.0.0.1`; Caddy завершён штатной командой `stop`. Основной экземпляр на3100 продолжает работать. В первом прогоне найдена дублировавшаяся директива Cache-Control, исправлена отложенной установкой заголовка и повторно проверена. Основной Cloudflare-сайт также прошёл read-only verifier без технических участников или развёртывания.

Проверка подготовленного файла без запуска внешнего сервера:

```powershell
$olympiadSource = Join-Path $env:USERPROFILE 'CodexProjects\olympiad-national-kitchens'
$olympiadCaddy = Join-Path $env:LOCALAPPDATA 'GKTSOlympiadTrial\v1\proxy-preparation\caddy-2.11.7\caddy.exe'
& $olympiadCaddy adapt --config (Join-Path $olympiadSource 'ops\windows-hosting\Caddyfile') --adapter caddyfile --pretty
```

После проверки WAN, DNS, брандмауэра и готовности данных используется `run` с тем же абсолютным `--config`. Команда запуска остаётся подготовленной, а не выполненной:

```powershell
& $olympiadCaddy run --config (Join-Path $olympiadSource 'ops\windows-hosting\Caddyfile') --adapter caddyfile
```

Штатная остановка продуктивного прокси: `& $olympiadCaddy stop --address 127.0.0.1:2019`. Она останавливает только Caddy; сервер и SQLite продолжают работать. Не применять эту команду к постороннему Caddy. Для службы сертификаты и ключи Caddy должны сохраняться в профиле того пользователя, от которого она работает.

## Что проверить до переключения

1. В панели роутера прочитать адрес **WAN/Internet IPv4** и сравнить с выходным адресом соединения без VPN. Частный WAN или диапазон `100.64.0.0/10` требует проверки CGNAT/второго NAT у провайдера; при несовпадении не назначать DNS на адрес VPN. Узнать, статический ли публичный адрес и разрешены ли входящие TCP 80/443.
2. Закрепить LAN-адрес ПК в DHCP. Подготовить правила роутера TCP 80→80 и 443→443 для этого ПК; 3100/2019 наружу не перенаправлять. Брандмауэр должен разрешать только нужные входящие порты Caddy. До фактического подключения эти настройки остаются не применёнными.
3. Получить реальный внешний тест 80/443 с другой сети. Проверить отдачу на реальных изображениях и репетицию участников из сети колледжа/мобильного оператора. Локальные 114 мс не заменяют этот результат.
4. Экспортировать текущие записи REG.RU. Предварительно уменьшить TTL целевого поддомена, выждать прежние 21600 секунд; затрагивать только `olympiada`, не NS всей зоны, почту или сайт колледжа. После готовности маршрута заменить его старый CNAME на A подтверждённого WAN-адреса. AAAA добавлять только при отдельно проверенном IPv6. Для HTTPS может потребоваться CAA; проверять текущие записи перед изменением.
5. Запустить продуктивный Caddy, получить публичный сертификат без отключения TLS-проверки. Выполнить внешний health, загрузку изображений, пробную попытку на отдельном тестовом проведении/стенде, сохранение/возврат/свидетельство и отрицательную проверку внешних admin-маршрутов. Зафиксировать источник проверки, DNS/TLS и задержки.

Если входящие подключения провайдер не даёт, выбрать туннель после проверки условий и доступности из РФ. [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/create-local-tunnel/) требует подходящей DNS-зоны в Cloudflare; простая запись в REG.RU на `UUID.cfargotunnel.com` не является готовым маршрутом. [Partial DNS](https://developers.cloudflare.com/cloudflare-one/faq/cloudflare-tunnels-faq/) требует отдельной конфигурации аккаунта. Не переносить NS всего колледжа и не покупать VPS как автоматическую замену заданному ПК.

## Обратное переключение

Сохранить экспорт DNS до изменения. При отказе нового маршрута остановить **новые старты** на ПК, дождаться/сохранить начатые попытки, сделать SQLite backup и вернуть прежнюю запись либо заранее проверенный Cloudflare-маршрут. Старый Яндекс CNAME — точка восстановления прежнего DNS, **не подтверждённый рабочий резервный сайт**. Cloudflare остаётся доступен по `olympiad-gkts.pages.dev`; не направлять туда новые официальные попытки без организационного решения о данных. DNS-откат не переносит ответы между SQLite и D1.
