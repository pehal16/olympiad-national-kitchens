# Пилот учебной платформы «Учебные работы»

## 1. Назначение документа

Этот регламент описывает фактически реализованный пилот режима «Учебные работы»: первичную настройку, работу преподавателя и студента, локальный запуск, выпуск на Cloudflare, резервное копирование, восстановление и приёмку.

Пилот рассчитан на постепенное подключение 10–15 групп и примерно 5 предметов. Начинать нужно с одной синтетической группы, затем с одной реальной группы и только после успешной приёмки расширять контур.

Режим работает отдельно от олимпиады и официального экзамена PM01. Его маршруты, данные о работах и интерфейсы не должны использоваться для изменения официальных результатов PM01.

Основные адреса:

- кабинет студента: `/learning.html`;
- кабинет преподавателя: `/learning-admin.html`;
- служебная проверка состояния: `/api/learning/status`;
- основной домен: `https://olympiada.gorlkts.ru`;
- прямой адрес Cloudflare Pages: `https://olympiad-gkts.pages.dev`.

Ежедневная подготовка расписания, лекций и документов регулируется отдельным документом [teacher-daily-workflow.md](teacher-daily-workflow.md). Текущий модуль автоматизирует выполнение и проверку учебных работ, но пока не получает расписание из ВКонтакте и не отправляет электронную почту.

## 2. Что входит в пилот

В текущем кабинете реализованы:

- роли администратора, преподавателя и студента;
- группы, предметы и учебные курсы;
- импорт состава группы с предварительной проверкой;
- вход студента через последовательный выбор группы и ФИО без логина и пароля;
- просмотр преподавателем состава группы без отображения внутренних идентификаторов доступа;
- редактор практических, лабораторных, тестовых, самостоятельных и домашних работ;
- опубликованные неизменяемые версии работ;
- назначение опубликованной версии группе, срок сдачи и число попыток;
- автосохранение ответов с контролем версии черновика;
- отправка и повторная отправка после возврата;
- автоматическая, ручная и смешанная проверка;
- рубрики, комментарий преподавателя, возврат на доработку и публикация оценки;
- закрытые ключи автоматической проверки, которые не передаются студенту;
- загрузка подтверждающих файлов;
- журнал результатов и экспорт CSV;
- аудит действий и история выставления оценки;
- безопасный синтетический выпуск для проверки полного сценария.

### 2.1. Типы блоков

Реестр `src/learning/block-registry.js` содержит 18 типов:

| Группа | Типы блоков |
|---|---|
| Без ответа | инструкция |
| Автоматическая проверка | один вариант, несколько вариантов, расчёт, соответствие, последовательность, классификация, кроссворд, требования безопасности |
| Смешанная проверка | краткий ответ, таблица, сборка блюда |
| Ручная проверка | развёрнутый ответ, ТТК, технологическая схема, файл, журнал наблюдений, рефлексия |

Смешанный блок может дать автоматическую часть результата, но профессиональную обоснованность преподаватель проверяет вручную. Автоматический балл не заменяет ручную проверку развёрнутых материалов.

### 2.2. Ограничения пилота

В текущей версии отсутствуют:

- автоматический приём расписания и замен из ВКонтакте;
- автоматическая отправка писем и уведомлений;
- массовый перенос существующих студентов между группами;
- автоматическое массовое резервное копирование всех учебных объектов Яндекс.Диска;
- интерфейс срока хранения и удаления персональных данных;
- полноценное управление несколькими преподавателями и разграничение общего каталога групп между ними;

Эти ограничения не мешают проверке одного учебного потока, но должны быть закрыты до массового обязательного использования платформы всеми группами.

## 3. Архитектура

```text
Браузер студента                      Браузер преподавателя
public/learning.html                  public/learning-admin.html
          \                                  /
           \                                /
             /api/learning/*
                    |
          src/learning/api.js
                    |
          src/learning/service.js
          проверка ролей, сценарии,
          публикация, сдача, оценивание
                    |
      +-------------+--------------+
      |                            |
локальный запуск              Cloudflare Pages
FileLearningRepository        D1LearningRepository
learning-state.json           binding DB
learning-files/               закрытая папка Яндекс.Диска
                              через серверный REST API
```

Основные компоненты:

- `server.js` подключает отдельный обработчик `/api/learning/*`;
- `src/learning/api.js` содержит HTTP-маршруты и защиту изменяющих запросов;
- `src/learning/service.js` реализует права, публикацию, назначения, сдачу и проверку;
- `src/learning/domain.js`, `validation.js` и `grading.js` содержат правила предметной области;
- `src/learning/serializers.js` удаляет закрытые ключи из студенческого ответа;
- `src/learning/repositories/file.js` хранит локальный контур;
- `src/learning/repositories/d1.js` хранит production-контур;
- `src/learning/files.js` проверяет и сохраняет вложения;
- `migrations/0003_learning_identity_catalog.sql` создаёт пользователей, роли, группы, предметы, курсы и темы;
- `migrations/0004_learning_works.sql` создаёт шаблоны, версии, блоки, ключи, рубрики и назначения;
- `migrations/0005_learning_submissions.sql` создаёт сдачи, ревизии, проверки, оценки, вложения, аудит и служебные журналы.

В Cloudflare метаданные находятся в базе `olympiad-gkts-db`. Это общая база проекта, поэтому восстановление D1 затрагивает не только «Учебные работы», но и другие табличные данные платформы. Студенческие файлы хранятся отдельно в подпапке `learning-files` настроенного каталога Яндекс.Диска. OAuth-токен доступен только серверной функции, а прямые публичные ссылки не создаются.

## 4. Роли и границы доступа

### 4.1. Администратор

Первая учётная запись получает роли `admin` и `teacher`. Она может:

- выполнить первичную настройку;
- развернуть синтетический пилот;
- выполнять все действия преподавателя.

### 4.2. Преподаватель

Преподаватель может:

- создавать группы, предметы и курсы;
- импортировать студентов;
- создавать, сохранять и публиковать работы;
- назначать работы доступным группам;
- видеть и проверять сдачи по назначениям, которые создал этот преподаватель;
- вернуть работу с обязательным комментарием;
- выставить баллы по рубрике и опубликовать оценку;
- выгрузить журнал.
- открыть состав доступной группы и проверить, что ФИО студента отображается в правильной группе.

### 4.3. Студент

Студент может:

- выбрать свою группу и ФИО и открыть закреплённый за этим профилем кабинет;
- увидеть назначенные ему работы;
- открыть черновик, сохранить ответы и приложить разрешённые файлы;
- отправить работу;
- увидеть возврат, комментарий, итоговый балл и оценку;
- повторно отправить исправленную версию.

Студент не получает закрытые ключи, чужие сдачи, внутреннюю рубрику проверки или прямой публичный адрес файла.

Выбор группы и ФИО не подтверждает личность криптографически. Студент обязан выбирать только себя; преподаватель организует работу так, чтобы исключить намеренный выбор чужого профиля. Для оценок и персональных данных повышенной чувствительности потребуется отдельный усиленный способ подтверждения личности.

## 5. Жизненный цикл данных

1. Преподаватель создаёт черновик работы.
2. Черновик проверяется и публикуется.
3. Опубликованная версия становится неизменяемой.
4. Для дальнейших исправлений сохраняется новый черновик и публикуется новая версия.
5. Назначение закрепляется за конкретной опубликованной версией.
6. Студент начинает сдачу со статусом `in_progress`.
7. Каждый ответ автосохраняется с номером ревизии черновика.
8. При отправке создаётся запечатанная ревизия ответа.
9. Объективные блоки получают автоматический результат.
10. Преподаватель принимает работу или возвращает её на доработку.
11. При повторной сдаче создаётся следующая запечатанная ревизия, предыдущая сохраняется.
12. Публикация оценки добавляется в журнал событий, а не переписывает историю незаметно.

Одновременное редактирование в двух вкладках защищено проверкой `expectedRevision`. При конфликте нужно загрузить свежую версию и проверить локальный черновик, а не пытаться принудительно перезаписать данные.

### 5.1. Черновик при сбое сети

- Несохранённые ответы сохраняются в браузере отдельно для пользователя и сдачи. После повторного открытия они восстанавливаются автоматически, только если серверная ревизия не изменилась.
- Если сервер уже получил тот же ответ, повторная запись не требуется и локальная копия очищается.
- Если на сервере более свежая версия или работа уже сдана, платформа не заменяет её локальным черновиком. Студент может скачать копию JSON, затем подтвердить продолжение с версией сервера. До решения конфликта редактирование и отправка закрыты.
- Переход к списку, другой работе и выход из кабинета сначала ожидают сохранения. При ошибке работа остаётся открытой. Кнопка «Сохранить» доступна и на компьютере, и на телефоне.
- Если браузер запрещает локальное хранилище или оно заполнено, сообщение прямо предупреждает не закрывать страницу: локальную копию сохранить не удалось. Локальное хранение не заменяет серверную резервную копию и не делает платформу полностью автономной без сети.

### 5.2. Просмотр учебных иллюстраций

В инструкции и заданиях на соответствие нажмите «Увеличить». Схема открывается целиком в отдельном окне; его можно закрыть крестиком, Escape или нажатием вне окна. Действие не меняет ответ студента и доступно в преподавательском предпросмотре. Увеличение не добавляет детализацию, которой нет в исходном рисунке.

## 6. Первичный локальный запуск

Локальный режим нужен для безопасной настройки контента, демонстрации и приёмки без реальных персональных данных.

### 6.1. Требования

- Windows и PowerShell;
- Node.js 22 или новее;
- актуальный репозиторий;
- свободный локальный порт, по умолчанию `3100`.

### 6.2. Установка и запуск

Из корня проекта:

```powershell
Set-Location "D:\Кодекс\olympiad-github-work"
npm.cmd ci

$env:PORT = "3100"
$env:STORAGE_BACKEND = "file"
$env:STORAGE_DIR = (Join-Path (Get-Location) "storage")
$env:LEARNING_ENABLED = "true"
$env:LEARNING_BOOTSTRAP_SECRET = "<СЕКРЕТ-ПЕРВИЧНОЙ-НАСТРОЙКИ>"
$env:LEARNING_PASSWORD_PEPPER = "<ПОСТОЯННЫЙ-ЛОКАЛЬНЫЙ-PEPPER>"

npm.cmd start
```

Значения секретов в примере заменяются случайными значениями из утверждённого менеджера секретов. Их нельзя записывать в репозиторий, документацию, общий чат или скриншот.

Для уже созданной локальной базы значение `LEARNING_PASSWORD_PEPPER` должно оставаться прежним: оно используется для защищённого входа преподавателя и совместимости с существующими записями.

После запуска открыть:

- `http://127.0.0.1:3100/learning-admin.html`;
- `http://127.0.0.1:3100/learning.html`.

Проверка состояния:

```powershell
Invoke-RestMethod "http://127.0.0.1:3100/api/learning/status"
```

До создания первого пользователя ожидаются `enabled: true`, `configured: false` и `requiresBootstrap: true`.

### 6.3. Локальные данные

Локальный репозиторий создаёт:

- `storage/learning-state.json` – пользователи, группы, работы, ответы и оценки;
- `storage/learning-state.json.backup` – предыдущая версия состояния перед последней записью;
- `storage/learning-files/` – вложения студентов.

Файл `.backup` является только одной аварийной копией предыдущего состояния. Он не заменяет регулярную резервную копию всего каталога вместе с файлами.

## 7. Первичная настройка администратора

1. Открыть `/learning-admin.html`.
2. На экране первого запуска ввести секрет `LEARNING_BOOTSTRAP_SECRET`.
3. Указать имя преподавателя.
4. Создать логин длиной от 3 до 64 символов.
5. Создать пароль длиной не менее 10 символов, содержащий буквы и цифры.
6. Войти под созданной учётной записью.
7. Проверить разделы «Обзор», «Работы», «Назначения», «Проверка», «Группы», «Журнал» и «Настройки».

Первичная настройка разрешена только при отсутствии пользователей. Повторный запрос настройки после создания первой учётной записи отклоняется сервером.

## 8. Секреты и параметры

### 8.1. Обязательные GitHub Actions secrets

Текущий workflow `.github/workflows/deploy-cloudflare.yml` использует:

| Секрет | Назначение |
|---|---|
| `CLOUDFLARE_API_TOKEN` | управление Pages, D1 и выпуском в пределах выданных прав |
| `CLOUDFLARE_ACCOUNT_ID` | идентификатор учётной записи Cloudflare |
| `ADMIN_PASSWORD` | пароль существующей административной части платформы и обязательное поле текущего workflow |
| `LEARNING_AUTH_SECRET` | постоянная секретная добавка к хэшам паролей учебного модуля |
| `LEARNING_BOOTSTRAP_SECRET` | секрет однократного создания первого администратора |
| `YANDEX_DISK_OAUTH_TOKEN` | закрытый серверный доступ к файлам студентов на Яндекс.Диске |
| `YANDEX_DISK_FOLDER` | базовый закрытый каталог; учебные файлы располагаются в его подпапке `learning-files` |

Workflow требует отдельные непустые `ADMIN_PASSWORD`, `LEARNING_AUTH_SECRET`, `LEARNING_BOOTSTRAP_SECRET` и `YANDEX_DISK_OAUTH_TOKEN`, проверяет OAuth-доступ к Диску и останавливает выпуск при ошибке. Один секрет нельзя использовать сразу для нескольких назначений.

Перед первым production-выпуском этой версии `ADMIN_PASSWORD` необходимо сменить: прежнее значение когда-то находилось в истории репозитория. Удаление значения из текущего файла настроек не отменяет обязательную ротацию.

`LEARNING_AUTH_SECRET` нельзя планово менять после создания преподавателей без процедуры повторной выдачи или миграции их паролей. Студенческий вход по группе и ФИО от этого секрета не зависит, но существующие внутренние записи сохраняются для совместимости.

`LEARNING_BOOTSTRAP_SECRET` можно сменить после первичной настройки: при уже существующем пользователе endpoint настройки всё равно закрыт. Значение всё равно должно оставаться секретным.

### 8.2. Параметры среды

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `LEARNING_ENABLED` | `true` | включает или выключает учебный модуль |
| `LEARNING_SESSION_HOURS` | `12` | срок пользовательской сессии |
| `LEARNING_LOGIN_FAILURE_LIMIT` | `5` | число неудачных попыток до временной блокировки |
| `LEARNING_LOGIN_LOCK_MINUTES` | `15` | длительность временной блокировки |
| `LEARNING_PASSWORD_ITERATIONS` | `210000` | число итераций PBKDF2-SHA256 |
| `LEARNING_FILE_MAX_BYTES` | `26214400` | глобальный предел файла, 25 МБ |
| `YANDEX_DISK_ENABLED` | `true` в Cloudflare | включает серверное файловое хранилище Яндекс.Диска |
| `YANDEX_DISK_FOLDER` | `/olympiad-results` | базовый закрытый каталог на Диске |
| `STORAGE_DIR` | `storage` в корне запуска | каталог локального состояния и файлов |
| `LEARNING_PASSWORD_PEPPER` | пусто | постоянный pepper локального режима |

В Cloudflare значение `LEARNING_AUTH_SECRET` передаётся сервису как password pepper. В локальном Node.js-запуске для этой цели применяется `LEARNING_PASSWORD_PEPPER`.

## 9. Выпуск на Cloudflare

### 9.1. Фактические ресурсы

В `wrangler.toml` закреплены:

- Pages-проект `olympiad-gkts`;
- D1 binding `DB` для базы `olympiad-gkts-db`;
- закрытое файловое хранилище Яндекс.Диска через серверные переменные `YANDEX_DISK_*`;
- `STORAGE_BACKEND = "cloudflare"`;
- `LEARNING_ENABLED = "true"`.

### 9.2. Рекомендуемый выпуск через GitHub Actions

1. Проверить и сохранить все обязательные GitHub Actions secrets из раздела 8.1.
2. Выполнить локальные проверки из раздела 15.
3. Зафиксировать проверенный код в `main` и отправить его в `origin/main`.
4. Дождаться workflow `Deploy to Cloudflare Pages`.
5. Проверить шаги `Run tests`, `Ensure Cloudflare resources`, `Apply D1 migrations`, `Build Cloudflare Pages bundle`, `Configure Pages secrets` и `Deploy Pages`.
6. Открыть production-адреса кабинетов и выполнить smoke-проверку.

Workflow автоматически:

- создаёт Pages-проект, если его нет;
- проверяет OAuth-доступ к Яндекс.Диску;
- находит или создаёт D1;
- применяет все миграции из `migrations/`;
- собирает `dist-cloudflare`;
- записывает Pages secrets;
- разворачивает ветку `main`.

Проверка последних запусков:

```powershell
gh run list --workflow deploy-cloudflare.yml --limit 3
```

Изменение только файлов `docs/**` не входит в path-фильтр автоматического выпуска. В таком случае workflow запускается вручную через `workflow_dispatch`, если требуется новый выпуск.

### 9.3. Ручные диагностические команды

Их следует использовать для диагностики и контролируемого обслуживания, а основной выпуск выполнять workflow.

```powershell
npm.cmd test
npm.cmd run build:cloudflare
npx.cmd wrangler d1 migrations apply olympiad-gkts-db --remote
npx.cmd wrangler pages deploy dist-cloudflare --project-name olympiad-gkts --branch main --commit-dirty=true
```

Ручной deploy допустим только если D1, Pages secrets и серверный доступ к Яндекс.Диску уже настроены. Команда не должна использоваться для обхода неуспешных тестов.

### 9.4. Проверка после выпуска

```powershell
Invoke-RestMethod "https://olympiada.gorlkts.ru/api/learning/status"
npm.cmd run verify:cloudflare -- https://olympiad-gkts.pages.dev
```

Вторая команда проверяет существующие общие и PM01-сценарии. Для учебного модуля дополнительно выполняется ручной сценарий из раздела 14, потому что отдельного production-verifier для `learning` в `package.json` пока нет.

## 10. Подготовка 10–15 групп и 5 предметов

### 10.1. Соглашения до импорта

До ввода данных составить таблицу:

| Поле | Пример |
|---|---|
| Код группы | `1-ПК-24А` |
| Название группы | `1-ПК-24А` |
| Код предмета | `МДК-03.01` |
| Название предмета | полное название по рабочей программе |
| Учебный год | `2026/2027` |
| ФИО студента | полное написание для списка выбора |

Коды нормализуются в верхний регистр, пробелы заменяются дефисами. Не следует создавать разные записи для вариантов написания одной группы.

### 10.2. Порядок наполнения

1. Создать все 10–15 групп.
2. Создать 5 предметов один раз.
3. Создать учебный курс, связывающий предмет, учебный год и группу.
4. Импортировать состав каждой группы отдельно.
5. Проверить, что все ФИО появились в составе правильной группы.
6. Открыть кабинет студента и проверить последовательность «группа → ФИО → кабинет».
7. Сообщить студентам адрес платформы и правило выбирать только собственное ФИО.
8. Только затем назначать реальные работы.

Импорт принимает от 1 до 60 студентов за операцию. Формат текста в интерфейсе:

```text
код;ФИО
С001;Иванов Иван Иванович
С002;Петрова Анна Сергеевна
```

Первая колонка используется как служебный код строки, вторая – как ФИО для списка выбора. Внутренний уникальный идентификатор создаётся платформой автоматически и студенту не показывается.

Текущий интерфейс создаёт один курс для одной выбранной группы. Поэтому при независимом продвижении 10–15 групп по 5 предметам получится 50–75 связок курс–группа. Если несколько групп должны идти строго по одному содержанию и срокам, API поддерживает несколько групп у курса, но такой массовый сценарий нужно отдельно проверить до применения.

## 11. Загрузка и публикация контента

### 11.1. Создание работы

В кабинете преподавателя:

1. Открыть «Работы».
2. Создать работу и выбрать курс.
3. Выбрать вид: практическая, лабораторная, тест, самостоятельная или домашняя.
4. Указать понятное название, тему и инструкцию.
5. Добавить только необходимые блоки.
6. Для автоматических блоков заполнить закрытый ключ.
7. Для ручных блоков добавить короткую и проверяемую рубрику.
8. Проверить максимальные баллы и обязательность блоков.
9. Выполнить предпросмотр.
10. Сохранить черновик.
11. Опубликовать только после методической проверки.

Опубликованную версию нельзя редактировать. Исправления вносятся в следующий черновик и публикуются новой версией. Уже выданное назначение остаётся привязанным к прежней версии, поэтому работа студента не меняется во время выполнения.

### 11.2. Назначение

1. Открыть «Назначения».
2. Выбрать опубликованную версию.
3. Выбрать курс и группу.
4. Указать дату открытия и срок сдачи.
5. Решить, разрешена ли поздняя сдача.
6. Задать от 1 до 10 попыток как параметр назначения.
7. Проверить название и целевую группу.
8. Опубликовать назначение.

Назначение создаётся только если в целевой группе есть студенты.

Число попыток проверяется на сервере. Повтор одного и того же запроса с тем же `Idempotency-Key` возвращает прежний результат и не расходует попытку повторно; новая ревизия сверх `max_attempts` отклоняется.

### 11.3. Файлы студентов

Глобально разрешены:

- PDF;
- DOCX;
- XLSX;
- PPTX;
- JPG и JPEG;
- PNG;
- WEBP.

Глобальный предел – 25 МБ. Конкретный блок может установить меньший предел и более узкий набор форматов. В синтетическом пилоте используются пределы 10 и 15 МБ.

Сервер проверяет имя, расширение, MIME-тип, размер и сигнатуру содержимого. Файл сохраняется только после успешной проверки, получает SHA-256 и остаётся доступным через защищённый API. OAuth-токен и прямые адреса Яндекс.Диска студенту не передаются.

## 12. Ежедневный процесс преподавателя

### 12.1. До публикации

1. Проверить расписание и замены по [teacher-daily-workflow.md](teacher-daily-workflow.md).
2. Сверить группу, тему, вид занятия и часы с поурочным планом.
3. При расхождении часов остановить подготовку и запросить решение.
4. Подготовить или обновить учебный материал.
5. Определить, какую часть студент выполняет в документе, а какую в интерактивном кабинете.
6. Создать или обновить черновик работы.
7. Проверить закрытые ключи и рубрику.
8. Выполнить предпросмотр от лица студента.
9. Опубликовать новую версию.
10. Создать назначение правильной группе с правильным сроком.

### 12.2. Во время выполнения

1. На «Обзоре» проверить активные назначения и очередь сдач.
2. Убедиться, что срок отображается корректно.
3. Не редактировать опубликованную версию, которую уже выполняют студенты.
4. При сообщении о пропавшем ответе проверить статус автосохранения и исключить одновременную работу в нескольких вкладках.
5. При проблеме с файлом проверить формат, фактический размер и соответствие блока.

### 12.3. Проверка

1. Открыть «Проверка».
2. Сверить студента, группу, предмет, работу и номер ревизии.
3. Проверить автоматические результаты.
4. Просмотреть развёрнутые ответы и все вложения.
5. Заполнить рубрику.
6. Если нужны исправления, написать конкретный комментарий и вернуть работу.
7. Если работа принята, указать итоговую оценку и опубликовать её.
8. Проверить запись в «Журнале».
9. При необходимости выполнить экспорт CSV явным действием.

### 12.4. В конце дня

1. Проверить работы без оценки и возвращённые работы.
2. Сверить ближайшие сроки.
3. Выгрузить журнал, если этого требует локальный порядок учёта.
4. Зафиксировать отклонения и инциденты.
5. Выполнить резервное копирование по установленному расписанию.

## 13. Резервное копирование и восстановление

### 13.1. Общие правила

- Метаданные и файлы образуют единый комплект.
- Резервная копия должна иметь дату, время, окружение и контроль ответственного лица.
- Копии содержат персональные данные и хэши паролей, поэтому хранятся в защищённом месте.
- Восстановление сначала репетируется на отдельном локальном или тестовом контуре.
- Перед production-восстановлением фиксируется текущая копия и явное решение ответственного.

### 13.2. Локальная резервная копия

Остановить сервер сочетанием `Ctrl+C`, затем выполнить копирование в заранее утверждённый каталог:

```powershell
$pilotStamp = Get-Date -Format "yyyyMMdd-HHmmss"
$pilotBackupRoot = "D:\CollegeBackups\learning"
$pilotBackup = Join-Path $pilotBackupRoot $pilotStamp
New-Item -ItemType Directory -Path $pilotBackup -Force | Out-Null

Copy-Item -LiteralPath ".\storage\learning-state.json" -Destination $pilotBackup
Copy-Item -LiteralPath ".\storage\learning-state.json.backup" -Destination $pilotBackup -ErrorAction SilentlyContinue
Copy-Item -LiteralPath ".\storage\learning-files" -Destination $pilotBackup -Recurse
```

Проверить, что в копии есть JSON и каталог файлов, а размер и число файлов не равны нулю. Отдельно сохранить используемый `LEARNING_PASSWORD_PEPPER` в менеджере секретов, а не рядом с резервной копией.

### 13.3. Локальное восстановление

1. Остановить сервер.
2. Проверить абсолютные пути источника и каталога `storage`.
3. Скопировать текущее состояние в отдельный каталог инцидента.
4. Скопировать выбранный `learning-state.json` в `storage/learning-state.json`.
5. Восстановить соответствующий каталог `learning-files`.
6. Запустить сервер с тем же `LEARNING_PASSWORD_PEPPER`.
7. Проверить `/api/learning/status`, вход преподавателя, одну работу, одно вложение и журнал.

Нельзя восстанавливать только JSON, если в нём есть ссылки на файлы, отсутствующие в выбранной копии.

### 13.4. Экспорт D1

Перед значимым выпуском или миграцией создать полный экспорт общей D1:

```powershell
$pilotStamp = Get-Date -Format "yyyyMMdd-HHmmss"
$pilotBackupRoot = "D:\CollegeBackups\cloudflare"
$pilotBackup = Join-Path $pilotBackupRoot $pilotStamp
New-Item -ItemType Directory -Path $pilotBackup -Force | Out-Null

npx.cmd wrangler d1 export olympiad-gkts-db --remote --output (Join-Path $pilotBackup "olympiad-gkts-db.sql")
```

Этот экспорт содержит общую базу платформы. Доступ к файлу должен быть ограничен так же строго, как доступ к production-базе.

### 13.5. Учёт и копирование файлов Яндекс.Диска

Список готовых вложений берётся из D1:

```powershell
npx.cmd wrangler d1 execute olympiad-gkts-db --remote --command "SELECT object_key, original_name, mime_type, byte_size, sha256 FROM learning_attachments WHERE status = 'ready';" --json
```

Каждый `object_key` из D1 соответствует пути `<YANDEX_DISK_FOLDER>/learning-files/<object_key>`. Папка должна оставаться закрытой: создавать публичные ссылки для работы кабинета не требуется.

Для резервного копирования следует синхронизировать или выгрузить целиком подпапку `learning-files` штатными средствами Яндекс.Диска, сохранить её вместе с экспортом D1 и сверить размеры и SHA-256 по манифесту. В репозитории пока нет команды автоматического пакетного экспорта этой папки. До её появления полный backup выполняется по утверждённой процедуре колледжа и проверяется на отдельном контуре.

### 13.6. D1 Time Travel

Wrangler поддерживает получение точки и восстановление D1:

```powershell
npx.cmd wrangler d1 time-travel info olympiad-gkts-db --timestamp "<RFC3339-ДАТА-И-ВРЕМЯ>" --json
npx.cmd wrangler d1 time-travel restore olympiad-gkts-db --bookmark "<BOOKMARK>"
```

Восстановление меняет всю удалённую базу `olympiad-gkts-db`, включая данные других режимов. Команду нельзя выполнять только ради одной учебной сдачи. Требуются:

1. подтверждённый инцидент;
2. актуальный экспорт текущего состояния;
3. проверенная точка восстановления;
4. остановка изменяющих операций;
5. согласование с владельцем всей платформы;
6. проверка D1 и соответствующего набора файлов Яндекс.Диска после восстановления.

## 14. Синтетический пилот

Кнопка «Развернуть пилот» доступна администратору и создаёт:

- одну синтетическую группу;
- 4 синтетических студенческих профиля;
- 5 предметов и 5 курсов;
- практическую работу № 1 по составлению заявки на сырьё с поэтапным расчётом и автоматической проверкой;
- практическую работу № 2 по пряностям и приправам с иллюстрациями, классификацией и производственными ситуациями;
- практическую работу № 3 по работе со сборником рецептур и пересчёту учебной карточки;
- практическую работу № 4 по организации рабочего места с интерактивной технологической схемой;
- промежуточный тест к практической работе № 5 по оборудованию для обработки и нарезки овощей и грибов.

Все пять работ относятся к первому курсу МДК 01.01 и следуют темам 1–5 рабочей программы 3-ПК-26. Перед переносом в реальную группу преподаватель проверяет используемые издания сборников рецептур, локальные инструкции на оборудование и действующие санитарные требования. Закрытые ключи находятся только в версии преподавателя.

После развёртывания студенческие профили сразу доступны через выбор пилотной группы и ФИО. Повторное нажатие не создаёт дубликаты.

Пилот следует разворачивать локально или в специально согласованном пустом контуре. В рабочей production-базе кнопка создаст реальные записи, хотя они и синтетические.

### 14.1. Полный тестовый сценарий

1. Администратор разворачивает пилот и проверяет состав синтетической группы.
2. Первый синтетический студент выбирает пилотную группу, своё ФИО и открывает кабинет.
3. Студент открывает каждую из пяти работ и проверяет сроки.
4. В тесте заполняются автоматические блоки.
5. В работе № 1 проверяются ввод через запятую, числовое округление и сводная заявка в килограммах.
6. В работе № 4 собирается схема не менее чем из семи этапов и трёх контрольных точек.
7. Загружается разрешённый PDF или DOCX и проверяется прогресс загрузки.
8. Проверяется отклонение запрещённого расширения и файла выше лимита.
9. Черновик закрывается и открывается заново, ответы должны сохраниться.
10. Работа отправляется один раз, а повторный API-запрос с тем же `Idempotency-Key` не должен создавать вторую ревизию.
11. Преподаватель открывает сдачу, проверяет ответы и возвращает её с комментарием.
12. Студент исправляет ответ и повторно отправляет работу.
13. Преподаватель заполняет рубрику, принимает работу и публикует оценку.
14. Студент видит результат в истории.
15. Преподаватель видит результат в журнале и скачивает CSV.
16. Второй синтетический студент не может открыть сдачу первого.

## 16. Безопасность и персональные данные

### 16.1. Реализованные меры

- пароль преподавателя хэшируется PBKDF2-SHA256 с солью и секретным pepper;
- токен сессии хранится на сервере только в виде SHA-256;
- cookie имеет `HttpOnly`, `SameSite=Lax` и `Secure` при HTTPS;
- изменяющие запросы требуют CSRF-токен и тот же origin;
- вход преподавателя ограничивает число неудачных попыток;
- публичный список входа содержит только активные группы и ФИО без логинов, паролей, оценок и ответов;
- сервер проверяет роль и принадлежность сдачи;
- закрытые ключи отделены от публичного содержимого;
- опубликованные версии и запечатанные ревизии защищены от незаметного изменения;
- события оценки и аудита в D1 защищены append-only триггерами;
- CSV защищается от формульной инъекции;
- файлы проверяются по расширению, MIME, размеру и сигнатуре;
- production-файлы хранятся в закрытой папке Яндекс.Диска и отдаются только через авторизованный маршрут платформы.

### 16.2. Организационные правила

- В первом прогоне использовать только синтетические фамилии и файлы.
- Перед реальным пилотом утвердить правовое основание обработки данных и локальный акт колледжа.
- Собирать только ФИО, группу, учебные ответы, необходимые файлы, оценки и служебные метки времени.
- Не помещать паспортные данные, адреса, телефоны и медицинскую информацию в задания или ответы.
- Не публиковать списки ФИО и оценок в общем чате.
- Перед началом работы объяснить студентам, что выбирать разрешается только собственное ФИО.
- Не использовать упрощённый вход для сведений, требующих усиленного подтверждения личности.
- Хранить экспорт журнала и резервные копии только в утверждённом защищённом каталоге.
- Ограничить доступ к GitHub, Cloudflare и backup-хранилищу принципом минимальных прав.
- Установить срок хранения ответов, файлов, журналов и резервных копий до массового запуска.
- Вести журнал лиц, которые имеют административный доступ.

### 16.3. Важные свойства секретов

- Потеря `LEARNING_AUTH_SECRET` или локального pepper лишает возможности проверять пароль преподавателя и нарушает совместимость старых учётных записей.
- Компрометация pepper требует отдельного плана: остановить преподавательский вход, сохранить данные, отозвать сессии и безопасно перевыпустить административные учётные данные.
- Секрет первичной настройки не является паролем преподавателя.
- GitHub Actions logs, скриншоты и команды не должны показывать значения секретов.

## 17. Инциденты

### 17.1. Кабинет не открывается

1. Проверить `/api/learning/status`.
2. Если `enabled: false`, проверить `LEARNING_ENABLED`.
3. Проверить последний Cloudflare workflow.
4. Убедиться, что статические файлы `learning.html`, `learning-admin.html`, `learning.css` и каталог `public/learning/` вошли в сборку.
5. Не изменять D1 до установления причины.

### 17.2. Ошибка «Хранилище учебных файлов не настроено»

1. Проверить Pages secrets `YANDEX_DISK_OAUTH_TOKEN`, `YANDEX_DISK_FOLDER` и `YANDEX_DISK_ENABLED`.
2. Проверить, что OAuth-токен действителен и базовая папка доступна для записи.
3. Проверить свободное место и ограничения загрузки в аккаунте Яндекс.Диска.
4. Проверить, что deploy выполнен с актуальным workflow.
5. Не просить студента многократно загружать один и тот же файл до устранения причины.

### 17.3. Студент не может войти

1. Проверить, выбрана ли правильная группа.
2. В кабинете преподавателя открыть «Группы» → «Открыть состав» и убедиться, что ФИО есть в составе.
3. Проверить, что группа и студент активны.
4. Обновить страницу, заново выбрать группу и ФИО.
5. Не создавать дублирующий профиль с другим написанием ФИО до проверки существующей записи.

### 17.4. Ответ не сохранился

1. Проверить индикатор автосохранения.
2. Проверить соединение.
3. Уточнить, не была ли работа открыта одновременно в двух вкладках.
4. При конфликте ревизии обновить работу и повторить только отсутствующее изменение.
5. Не пытаться править `learning-state.json` или D1 вручную во время работы сервера.

### 17.5. Ошибка загрузки

1. Проверить формат и расширение.
2. Проверить размер блока и глобальный предел.
3. Убедиться, что содержимое действительно соответствует заявленному типу.
4. Проверить закрытую папку Яндекс.Диска или локальный каталог.
5. Не переименовывать исполняемый или неизвестный файл в разрешённое расширение.

### 17.6. Неверная опубликованная работа

1. Не изменять опубликованную версию в базе.
2. Создать и проверить новый черновик.
3. Опубликовать новую версию.
4. Новые назначения создавать из новой версии.
5. Для уже выполняемой работы согласовать педагогическое решение и зафиксировать его.

### 17.7. Ошибка после deploy

1. Зафиксировать время, commit и затронутые маршруты.
2. При необходимости выключить только учебный модуль через `LEARNING_ENABLED`, не удаляя данные.
3. Не откатывать D1 автоматически вместе с кодом.
4. Для совместимых изменений предпочитать исправляющий выпуск вперёд.
5. Восстановление общей D1 выполнять только по процедуре раздела 13.6.

### 17.8. Подозрение на утечку

1. Ограничить доступ к кабинету и Cloudflare.
2. Зафиксировать время и возможный объём данных.
3. Отозвать административные доступы и сессии по согласованной процедуре.
4. Не менять `LEARNING_AUTH_SECRET` без плана восстановления преподавательского доступа.
5. Сохранить audit evidence и не пересылать персональные данные в открытом виде.
6. Действовать по локальному порядку уведомления об инцидентах колледжа.

## 21. Аварийное восстановление администратора

Ручной workflow `Recover learning administrator` предназначен только для случая, когда у единственного действующего администратора утрачены или перестали подходить данные входа. Для него используются GitHub Secrets `LEARNING_RECOVERY_PASSWORD` и действующий `LEARNING_AUTH_SECRET`. Workflow сам вычисляет соль и PBKDF2-SHA-256-хэш внутри GitHub Actions; пароль, хэш и соль не печатаются в журнал и не записываются в репозиторий. Устаревшие secrets `LEARNING_RECOVERY_PASSWORD_HASH` и `LEARNING_RECOVERY_PASSWORD_SALT` workflow не читает, поэтому их можно удалить.

Процедура требует точную контрольную фразу, прекращает работу, если активных администраторов не ровно один, заменяет только логин и проверочные данные пароля, отзывает старые сессии, очищает блокировку входа и добавляет событие аудита. Группы, назначения, работы, ответы, вложения и оценки не изменяются. Локальную копию данных входа разрешено хранить только в защищённом Windows DPAPI-файле; после использования пароль восстановления нужно заменить, если к нему мог получить доступ кто-либо ещё.
